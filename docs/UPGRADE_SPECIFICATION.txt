## 2.2 Multi-currency model
- Add currency support: plans and credit_packs get explicit price columns per supported currency (at minimum KES and USD), or a prices table keyed by (item, currency). Payments store `currency` and `amount_minor` (integer minor units, no floats for money). Update packages/core/src/money.ts and its tests accordingly.
- Remove every hard-coded 'KES' assumption (checkout creation, Pesapal webhook verification, admin revenue reporting). Verification must compare against the STORED payment currency and amount.
- Admin revenue reporting must group by currency and never sum across currencies.
- Provider/currency routing rule: Pesapal defaults to KES; PayPal defaults to USD. Confirm with Pesapal's current docs and the user's account whether USD via Pesapal is enabled; do not assume.

## 2.3 PayPal integration
Use PayPal's current REST APIs (verify docs). Required behavior:
- Create orders server-side (Orders API v2) with intent CAPTURE, amount/currency taken from the server's price tables only (never from the client), our unique reference stored in custom_id/invoice_id, and a PayPal-Request-Id idempotency header on creation and capture calls.
- The client approves the order on PayPal; our SERVER then captures it. Never mark a payment paid because the browser says so or because a return URL was hit.
- Fulfill only when a server-side capture/lookup shows status COMPLETED for the exact order ID we created, and amount, currency, and our reference match the stored payment row. Then call fulfill_verified_payment.
- Webhook endpoint: verify authenticity with PayPal's webhook signature verification API using the configured webhook ID (fail closed if verification fails or the ID is unset). Treat webhook bodies as hints; always re-fetch the order/capture from PayPal before acting. Make processing idempotent by storing processed event IDs.
- Handle PAYMENT.CAPTURE.PENDING (hold, do not fulfill), DENIED, REFUNDED, REVERSED and dispute events: mark the payment accordingly, reverse or suspend entitlements through a DB function that is itself idempotent and audited, notify the workspace owner and admins.
- Sandbox vs live selected by PAYPAL_ENV; fail closed in production if live credentials or the webhook ID are missing. Env vars: PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, PAYPAL_WEBHOOK_ID, PAYPAL_ENV. Update .env.example and config validation.
- Billing model: implement one-time payments that grant a billing period (subscription period extension) and top-ups. Also implement period expiry, grace handling, downgrade-to-free on expiry, and renewal reminder notifications, since one-time payments do not auto-renew. Document clearly that auto-renewing subscriptions via PayPal Subscriptions are NOT implemented unless you implement and test them.

## 2.4 Provider abstraction and risk control
- Introduce a PaymentProvider interface (createCheckout, verify, handleWebhook, refund/reversal mapping) with PesapalProvider and PayPalProvider implementations, so billing routes contain no provider-specific logic and a future gateway can be added without touching routes.
- Add admin-controlled feature flags to enable/disable each provider independently at runtime, and show only enabled providers in the UI. Reason: PayPal accounts in Kenya have been restricted or frozen in the past, and one provider must never be a single point of failure.
- Add a reconciliation job and admin screen: list payments stuck in processing/pending beyond a threshold, re-query the provider, and resolve safely. Write a runbook for it.

## 2.5 Billing tests
- Unit/integration tests (provider HTTP mocked only at the fetch boundary) covering: unverified, wrong-amount, wrong-currency, wrong-reference, replayed, pending, denied, refunded, reversed and failed events never fulfill or always reverse correctly; a verified one fulfills exactly once, even with concurrent duplicate webhooks plus a manual reconciliation.
- Test that a client cannot choose its own price, currency, plan or credit quantity.
- Test provider flags (disabled provider rejects checkout).
- Test period extension, expiry and downgrade logic.
